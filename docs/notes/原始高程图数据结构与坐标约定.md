# 原始高程图数据结构与坐标约定

本文记录 `elevation_mapping_cupy` 中原始高程图 topic 的数据结构、layer 含义，以及 `GridMap.data` 中行列和 `odom` 坐标的对应关系。

## 启动命令

Go2 双雷达配置的典型启动命令：

```bash
ros2 launch elevation_mapping_cupy go2_mid360.launch.py \
  robot_config:=go2/dual_lidar.yaml \
  launch_rviz:=true
```

这个 launch 会启动 `elevation_mapping_node`，加载：

- `config/core/core_param.yaml`
- `config/setups/go2/dual_lidar.yaml`

`dual_lidar.yaml` 中配置了两个点云输入：

```text
/cloud_registered
/utlidar/cloud
```

并配置了两个高程图输出：

```text
/elevation_mapping_node/elevation_map_raw
/elevation_mapping_node/elevation_map_filter
```

## 原始输出 topic

### `/elevation_mapping_node/elevation_map_raw`

消息类型：

```text
grid_map_msgs/msg/GridMap
```

默认 layer：

```text
elevation
traversability
variance
```

其中 `elevation` 是原始融合后的高度层。

### `/elevation_mapping_node/elevation_map_filter`

消息类型：

```text
grid_map_msgs/msg/GridMap
```

默认 layer：

```text
min_filter
smooth
near_base_filtered
despiked
inpaint
elevation
```

各 layer 的直观含义：

| Layer | 含义 |
| --- | --- |
| `elevation` | 原始融合后的高度层 |
| `min_filter` | 局部最小值滤波结果 |
| `smooth` | 平滑后的高度层 |
| `near_base_filtered` | 机器人底盘附近过滤后的高度层 |
| `despiked` | 去尖刺后的高度层 |
| `inpaint` | 补洞后的高度层 |

对局部规划、控制、学习模型输入等下游任务，通常优先使用：

```text
topic: /elevation_mapping_node/elevation_map_filter
layer: inpaint
```

如果下游必须严格区分真实观测区域和补洞区域，则不应只依赖 `inpaint`，需要额外结合有效性、NaN 或 mask 信息。

## GridMap 的 rolling map 语义

`core_param.yaml` 中默认：

```yaml
map_frame: odom
base_frame: base_link
resolution: 0.1
map_length: 20.0
```

在 Go2 配置中会覆盖为：

```yaml
map_frame: odom
base_frame: base
corrected_map_frame: odom
```

这里的 `20m x 20m` 不是固定在 `odom` 原点的全局地图，而是一个随机器人位置移动的局部 rolling map。

例如：

```text
机器人在 odom 下 x=0, y=0:
  地图覆盖约 x=-10..10, y=-10..10

机器人移动到 odom 下 x=25, y=0:
  地图中心随机器人移动到 x=25, y=0
  地图覆盖约 x=15..35, y=-10..10
```

旧区域离开 rolling map 窗口后会被移出内部数组，新进入窗口的区域会重新初始化并等待新点云填充。

## rolling map 是否随机器人朝向旋转

不会。

原始 GridMap 的中心会跟随机器人在 `odom` 中的位置移动，但地图方向始终对齐 `odom`，不会随 `base` 的 yaw 改变而旋转。

代码依据：

```python
# elevation_mapping_node.py
gm.header.frame_id = self.map_frame
gm.info.pose.position.x = self._map_t.x
gm.info.pose.position.y = self._map_t.y

gm.info.pose.orientation.x = 0.0
gm.info.pose.orientation.y = 0.0
gm.info.pose.orientation.z = 0.0
gm.info.pose.orientation.w = 1.0
```

发布出去的 GridMap 姿态固定为单位四元数，所以它在 `odom` 下只是平移，不随机器人朝向旋转。

内部位姿更新会读取 `odom -> base`：

```python
trans = np.array([t.x, t.y, t.z], dtype=np.float32)
rot = quaternion_matrix([q.x, q.y, q.z, q.w])[:3, :3].astype(np.float32)
self._map.move_to(trans, rot)
```

但 `move_to()` 中用于 rolling shift 的是平移差：

```python
delta = position - self.center
delta_pixel = xp.around(delta[:2] / self.resolution)
self.center[:2] += delta_xy
self.shift_map_xy(-delta_pixel)
```

所以：

```text
机器人移动: rolling map 中心跟随移动
机器人原地转身: rolling map 不旋转
GridMap X/Y 方向: 始终对齐 odom X/Y
```

## `/elevation_map_filter.data` 的行列定义

`GridMap.layers` 和 `GridMap.data` 一一对应。

例如：

```python
idx = msg.layers.index("inpaint")
layer_msg = msg.data[idx]
```

每个 `layer_msg` 是 `std_msgs/msg/Float32MultiArray`。发布时使用的是 GridMap 风格的 column-major 编码：

```python
layout.dim[0].label = "column_index"
layout.dim[0].size = cols
layout.dim[1].label = "row_index"
layout.dim[1].size = rows
data = arr.flatten(order="F")
```

因此从一维 `data` 还原二维数组应使用：

```python
arr = np.array(layer_msg.data, dtype=np.float32).reshape((rows, cols), order="F")
```

发布后的二维数组 `arr[row, col]` 和 `odom` 的关系是：

```text
row 增大 -> odom_x 减小
col 增大 -> odom_y 减小
```

近似坐标公式：

```python
x_odom = center_x + ((rows - 1) / 2.0 - row) * resolution
y_odom = center_y + ((cols - 1) / 2.0 - col) * resolution
z = arr[row, col]
```

其中：

- `center_x = msg.info.pose.position.x`
- `center_y = msg.info.pose.position.y`
- `resolution = msg.info.resolution`

直观理解：

```text
arr[0, 0]              -> rolling map 的 +odom_x, +odom_y 角
arr[rows-1, 0]         -> rolling map 的 -odom_x, +odom_y 角
arr[0, cols-1]         -> rolling map 的 +odom_x, -odom_y 角
arr[rows/2, cols/2]    -> rolling map 中心，接近机器人当前位置
```
